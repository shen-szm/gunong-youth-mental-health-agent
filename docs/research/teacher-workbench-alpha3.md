# 教师支持工作台开源项目对比与落地方案

版本：5.1.0-alpha.3  
日期：2026-08-24

## 对比结论

| 项目 | 功能设计 | 技术架构与技术栈 | 优点 | 不直接采用的部分 |
| --- | --- | --- | --- | --- |
| [Student Insights](https://github.com/studentinsights/studentinsights) | 教师花名册、学生纵向记录、角色化视图、干预记录 | Ruby on Rails、PostgreSQL、React、后台数据导入任务 | 以学生为中心；强调数据来源、权限和学校实际工作流程 | 架构较重，历史前端兼容成本高；不适合直接嵌入当前 Vue/FastAPI 项目 |
| [Chatwoot](https://github.com/chatwoot/chatwoot) | 收件箱队列、筛选、分配、标签、快捷操作、团队协作和报表 | Ruby on Rails、Vue、PostgreSQL、Redis/ActionCable | “先处理什么”非常清楚；列表—详情结构成熟；操作反馈和状态体系完整 | 面向客服会话，不具备未成年人心理安全和原文审批边界 |
| [Dify](https://github.com/langgenius/dify) | Agent 工作流、节点状态、运行记录、结构化输出和人工介入 | Python、TypeScript/React、PostgreSQL、Redis、Celery | Agent 执行过程可观察；节点输入输出、失败与人工确认边界清晰 | 通用工作流画布复杂度过高；不能把模型推理过程直接展示给教师 |
| [Medplum](https://github.com/medplum/medplum) | 权限化记录、审计、任务和结构化健康数据 | TypeScript、React、FHIR、PostgreSQL | 权限、审计和结构化任务设计严谨 | 医疗语境过强；本项目不应被设计成诊断或临床系统 |

## 采用的组合方案

教师端采用“队列式支持数字员工”而不是传统统计后台：

1. **今日工作台**：聚合待处理预警、待审批申请、可继续工单和教师确认任务。
2. **列表—工作区**：学生列表保持简洁，详情区只展示当前权限阶段和下一步。
3. **可核验 Agent**：今日页只汇总当前队列事实；进入授权工单并真实执行后，才展示权限核验、安全分流、证据定位、支持任务和人工确认状态，不展示思维链。
4. **描述性情绪记录**：移除平均情绪分和健康状态阈值，仅展示记录次数、标签分布、时间变化、来源和非测评边界。
5. **权限不旁路**：普通教师继续申请工单并经管理员教师审批；管理员教师直达仍记录审计。

## 当前项目落地

- 保持 Vue 3 + Vite 前端与 FastAPI + SQLAlchemy 后端，不引入第二套框架。
- 教师端新增固定应用壳、分组侧栏、全局学生搜索、今日任务队列和 Agent 状态摘要。
- 原支持工单、预警、学生记录、AI 班会、权限审批和账号职责功能继续复用现有 API。
- 视觉采用深墨绿工具栏、低彩度内容面和少量液态玻璃；品牌像素元素只用于标识，不干扰高密度工作任务。
- 所有敏感原文仍只在现有授权接口中读取，界面重构不扩大任何教师权限。
