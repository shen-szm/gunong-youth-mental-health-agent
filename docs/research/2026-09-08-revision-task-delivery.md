# PC 补充任务闭环

状态：本地已实现，未上线；持久化执行试点仍默认关闭。仅新增 PC 入口，不做移动端优化。

## 用户流程

1. 在任务报告中退回并填写审核意见。
2. 点击「检查补充资料」：无新记录时等待补充；发现紧急信号则优先人工处理；只有新增授权记录时才出现「准备补充计划」。
3. 创建独立补充任务，展示原报告、资料增减和不变的授权范围/执行顺序。原任务和原报告保持原样。
4. 教师重新确认新计划后显式执行，生成/复用当前资料对应的独立报告，再走原有审核流程。

PC 控件与差异区域使用 impeccable skill，沿用已有双栏工作区。原报告审核意见不传给模型，也不存进 checkpoint。本轮仅基于新增资料准备新报告，不声称模型已理解并自动解决自由文本退回要求。

## 实现与安全

- 新增 POST `/api/teacher/tasks/durable-plans/{task_id}/revision-plans`，复用 LangGraph 计划确认与已有四步真实工具图。
- 服务端重做修订检查，拒绝无新增资料、未退回、未交付及安全优先情况。仅继承原授权目标，不能从请求指定其他学生或扩大范围。
- 任务元数据保存原任务/报告引用、工单引用、资料 SHA-256 和增减数量；这些参与确认摘要。资料正文只在请求内计算摘要，不进入任务存档。
- 同一原任务、同一工单及同一资料摘要派生同一任务标识；重复创建返回同一任务。资料变化可形成另一份待确认计划，不能借旧确认执行新资料。
- 执行前重新检查原任务存在、原报告仍退回、报告完整性和权限，并核对锁定的资料摘要。读取/生成阶段也检查资料未变；原地修改已有记录同样导致拒绝执行。
- 新旧报告通过补充任务的 revision 元数据关联。源工单变化时，既有报告表的 revision_number 可能从 1 开始；不能把它误认为跨工单连续版本号。
- 返回原任务只读状态；刷新待确认补充任务不自动确认或执行。

## 验收

后端集成覆盖：无新增资料禁止创建、同源重复创建同一任务、未确认禁止执行、旧摘要不能确认新计划、确认后原地修改资料拒绝执行、新计划新报告、旧任务保持原报告、成功重复执行不重复报告。原有职责撤销和审批截止限制测试继续保留。

PC 真实接口浏览器验收：退回 → 等待补充 → 隔离学生账户提交记录 → 检查 → 创建补充计划 → 刷新恢复 → 确认 → 执行 → 报告审核签署；同时验证 1280/1440/1920 宽度布局。没有使用线上学生资料，不能将此测试计为真实使用效果。

## 未完成事项

模型按结构化反馈选择不同工具顺序、自由文本反馈转补充目标、跨审批范围的新授权流程、任务主动过期清理和生产部署仍未完成。当前差异是资料/任务关系差异，四步工具顺序不变。资料不再变化也不代表证据充分，教师仍须核对退回问题是否解决。
